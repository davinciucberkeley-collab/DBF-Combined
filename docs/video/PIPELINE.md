## 4. How a film is built (what the stages do)

1. `load_film` reads the shot list: scenes, shots (duration, camera keys with Hermite interpolation and `hold`, part modes, tags, readouts, mechanism sweeps, SITL windows, FEA panels).
2. `film_driver` starts Blender workers (`render` subcommand) on contiguous frame ranges; each worker builds the CAD stage from the current model, poses parts per frame (mechanism from AR-001 table, aircraft from the SITL log, props illustrative), writes raw PNGs, and writes `map_<first>.json`.
3. Pillow pass (8 processes): titles, tags (SIMULATED / illustrative), readouts whose numbers come from source files at draw time (`src_val`), 0.2 s dips to the stage colour at scene joins.
4. `encode` assembles the named PNG list (a name may repeat for static holds) into MP4 through the VSE. Dedupe: identical frames are rendered once.

## 6. Camera clearance check (category: interference)

`--cam-check` renders nothing. For every frame of every shot, in part-local BVHs: camera inside any visible part (closed-mesh ray parity on two axes), nearest-surface distance against `near_m` 0.05, and the first non-x-ray hit on the line camera to subject (flag if more than 0.08 m before it). Shot keys `los: false` (target is only a framing offset) or `los: [x,y,z]` set the subject. Output `film/cam-clearance.json` (the driver copies it there, overwriting it: the highlight check must be saved under a different name afterwards).

```
python $R --shot-list $F/shots-main.json --cam-check --width 1920 --height 1080 --fps 60
python $R --shot-list $F/shots-highlight.json --cam-check --width 1920 --height 1080 --fps 60 --work <SCRATCH>
cp $F/cam-clearance.json $F/cam-clearance-highlight.json     # then restore the main file from git or the copy
```

Results of record: main 6,960 frames, 0 inside any part, nearest 0.0679 m (shot 3.2), line of sight blocked in 10 frames (shot 2.2, the target motor's own prop blade, accepted); highlight 1,452 frames, 0 inside, 0 blocked. ## 10. Known limits

- No ffmpeg or ffprobe (PD-006): `ffprobe`-based verification is replaced by Blender decode; Blender's decoder is the only one tested; no audio; scene concatenation is done inside the VSE encode (cuts via the PNG list), not with ffmpeg.
- Decode is sampled (first, every 60th, last, scene joins), not a full-stream decode: 117 of 6,960 main frames, 26 of 1,452 highlight frames, 13 and 7 clip frames. Frame counts and fps come from container metadata.
- The mean-absolute-difference join test cannot separate a hard cut from motion on a mostly white stage (PLAYBACK-T033 notes).
- Prop spin is illustrative (category), 47 deg per frame, on only when the logged thrust of that motor exceeds 0.05 N; the plant RPM is not logged. S4 time scale changes at shot joins (x9.6, x2.8, x2.8, x26, x3.6) are changes of speed, readout shown; the log clock is not blended across joins (m-4, open).
- Ground contact in S4 is geometric (z = 0), not deformation; the elevon sign convention (+ = trailing edge down) is taken from the `a_aero` use, not independently checked; SITL run Z5_gb0 predates D-207 geometry and uses EST aero; FEA panels use EST allowables (D-207 rule).
- Motion blur and DOF flags (`--dof`, `--motion-blur`) were never exercised in a full render (motion blur probably has no effect because objects are posed directly per frame: unverified).
- The rendered frames live in `%TEMP%` and are lost when it is cleaned; a new film run clears `map_*.json` in its work folder; a rerun is the only way to re-cut clips then. The film lists and clips depend on the exact frame names of the T-031 main run.
- Hashes of the rendered videos change if Blender, the CAD, the encoder settings or a source record changes; reproduce by comparing frame counts, durations and overlay numbers, not file hashes.
- Dependencies on git-ignored record folders (section 2): they must be force-added or regenerated before a clean-tree rerun.
