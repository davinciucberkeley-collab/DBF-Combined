Status: `PROPOSED` requirement set (A2, 2026-11-09), re-derived from `config-study/REQUIREMENTS-PROPOSED.md` P1–P25 for the configuration in `CONFIGURATION.md`. 57 requirements: 18 shared ids from `params/claims.json` (A1) and 39 added in `team/A2/claims.json`. Every one has an owner, a value with a source, and a verification method. Status per requirement: `VERIFICATION-MATRIX.md`. Generated by `team/A2/build_requirements.py` from `team/A2/requirements.json` — edit the JSON, not this file.

## How to read

| Column | Meaning |
|---|---|
| ID | Proof-chain requirement id. A claim closes it by naming it in `verifies`. |
| P | The P1–P25 line(s) of `REQUIREMENTS-PROPOSED.md` it comes from. |
| Value · Unit | What a claim is tested against; `—` for text requirements (closed by inspection or demonstration). |
| Source | Where the number lives: a `params.json` key, an `ASM-A2-…` limit (A2's `PROPOSED` number, table at the end), or a decision file. |
| Owner · Method | Role that writes the claim; A analysis · I inspection · T test · D demonstration. Support roles: the matrix. |

## How a role closes a requirement

- Numeric: `kit.claim(..., limit={'op': '<=', 'ref': 'P:requirements.…'} or 'ASM-A2-…', verifies=['R-…'], how=…)` → `CHECKED` when the calculation re-runs with checked inputs and the margin is ≥ 0.
- Tested: add `kit.test(..., verifies=['CL-…'], state='run', result='pass', measured=…, evidence=<file>)` → `VERIFIED`.
- Inspection or demonstration (text requirement): a claim with no calc (`value` 1, `unit` `-`, `status` `PROPOSED`) plus a test node whose `evidence` names the file in the matrix → `VERIFIED` when it has run and passed.
- Always give `how` and, for hardware, `parts` (ids from `interfaces.json`). Re-run your script after any parameter change.
